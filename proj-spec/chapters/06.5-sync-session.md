# 6.5 Sync session

> **Spec chapter:** Bootstrap, live bidirectional apply, conflicts, echo suppression.
> **Parent:** [6. Components](06-components.md)
> **Index:** [README.md](../README.md)

A **session** is one plugin connection to one rbx-sync `serve` process.

## Session lifecycle

1. **Handshake** — `POST /v1/session` ([§7.1](07.1-http-api.md)). rbx-sync replaces any previous session and closes its stream with `SESSION_REPLACED`.
2. **Compare** — plugin sends Roblox Studio snapshot; rbx-sync compares to disk snapshot (nodeId, class, source).
3. **Bootstrap choice** if unequal — user picks Disk wins, Roblox Studio wins, or Cancel.
4. **Live** — both directions until disconnect or replace.
5. **End** — plugin Disconnect, Roblox Studio close, rbx-sync exit, or replace.

Cancel leaves disk and Roblox Studio unchanged and does not enter live.

## Revision initialization

A fresh `serve` process assigns **revision 1** to every currently mapped disk node (Folders included). There is no “revision 0 on disk” after serve start; `baseRevision` **0** is only valid on live `upsert`/`delete`/`rename` for a `nodeId` rbx-sync does not yet have.

| Path | How each side gets revisions before live |
|------|------------------------------------------|
| Compare `equal: true` | Plugin `GET /v1/snapshot` and stores each node’s `revision` (all `1` on a fresh serve unless a prior live session in this process already incremented them). rbx-sync already has the table. |
| Disk wins | `POST /v1/bootstrap/apply` `{ "direction": "disk-to-studio" }` returns `{ "nodes": [...] }` with `revision` on each node (1 on a fresh serve). Plugin applies those nodes and stores revisions. rbx-sync keeps the same table. |
| Roblox Studio wins | rbx-sync writes the submitted nodes, sets each present mapped node to revision **1**, returns `{ "applied": [{ "nodeId", "revision": 1 }] }`. Plugin stores those revisions. Nodes omitted from the Roblox Studio snapshot are deleted on disk and dropped from the table. |

After this step, live apply uses [Live apply](#live-apply). Reconnect to a **still-running** serve adopts whatever revisions `GET /v1/snapshot` reports (they may be greater than 1).

## Bootstrap

| Choice | rbx-sync does | Plugin does |
|--------|---------------|-------------|
| Disk wins | No disk writes | Apply full disk snapshot to mapped Roblox Studio roots (create/update/delete mapped nodes only) |
| Roblox Studio wins | Write full Roblox Studio snapshot to disk (create/update/delete mapped files only) | No Roblox Studio writes for that batch |
| Cancel | — | — |

Delete during bootstrap applies only to **mapped** nodes. Unmapped Roblox Studio instances and unmapped disk files (for example `README.md` outside mapping) stay.

Revision tables after Disk / Roblox Studio wins follow [Revision initialization](#revision-initialization).

## Live apply

Each node has a `revision` (unsigned integer). The side that mutates increments it.

Apply payload entries include `baseRevision` equal to the last revision that side knew. The receiver:

- If `baseRevision` equals current revision → apply, set revision to `baseRevision + 1`, ack.
- If node is new (`baseRevision` 0) and absent → create, revision 1.
- Otherwise → **CONFLICT**, do not apply that entry; other entries in the same batch MAY apply.

## Conflict UI

For each conflicting `nodeId`, the plugin MUST offer **Keep disk** or **Keep Roblox Studio** (and MAY offer skip). Skip leaves both sides unchanged for that node and retries later only if the user applies again.

Keep disk: plugin applies rbx-sync’s current source/class/presence.  
Keep Roblox Studio: plugin `POST /v1/apply` with `baseRevision` equal to rbx-sync’s current revision (force) using field `"force": true` on that change only.

`force: true` is valid only as a conflict resolution from the plugin after a `CONFLICT` for that nodeId. rbx-sync MUST reject `force` on first-try live applies (`BAD_REQUEST`).

## Echo suppression

| Rule | Detail |
|------|--------|
| Origin tag | Events include `origin`: `disk` or `studio` |
| Self-write ignore | rbx-sync ignores filesystem events for paths it wrote in the last 500 ms |
| Self-apply ignore | Plugin ignores DataModel/source signals caused by applying a disk event for that node until the apply finishes |
| Revision | A side MUST NOT send an apply for a node whose revision it just set from the other side |

## Disconnect

On disconnect, rbx-sync keeps files as last written. The plugin stops listeners. Reconnect starts at handshake again (new compare). The access token is unchanged until the rbx-sync process exits.
