# 10.2 Windows and WSL

> **Spec chapter:** Supported topologies for Roblox Studio (Windows) plus rbx-sync (Windows or WSL).
> **Parent:** [10. Operations](10-operations.md)
> **Index:** [README.md](../README.md)

Roblox Studio is a **Windows** process. rbx-sync may run on Windows, in WSL, or on native Linux. Only T1 and T2/T3 participate in a live Roblox Studio session. Native Linux without WSL forwarding is for running rbx-sync and tests, not for reaching Roblox Studio over the LAN (loopback only). The plugin always connects to `127.0.0.1` on the Windows side unless mirrored networking makes WSL loopback the same host.

## Supported topologies

| ID | Project files | rbx-sync process | How the plugin reaches rbx-sync |
|----|---------------|------------------|---------------------------------|
| T1 | Windows path (`C:\…`) | Windows `rbx-sync.exe` | `127.0.0.1:29850` (default, preferred) |
| T2 | WSL tree (`~/…` or `/mnt/c/…`) | WSL `rbx-sync` | Windows Roblox Studio → `127.0.0.1:29850` **if** WSL localhost forwarding or **mirrored** mode is on |
| T3 | Windows path via `/mnt/c/…` | WSL `rbx-sync` | Same as T2; file watch uses the Linux view of the path |

T1 is the default recommendation. T2/T3 require Microsoft WSL localhost behavior described in [references.md](../../references.md).

## Binding

rbx-sync still binds **loopback only**. Do not bind `0.0.0.0` to “fix” NAT. If Roblox Studio cannot connect in T2:

1. Enable mirrored mode (`networkingMode=mirrored` in `.wslconfig`), `wsl --shutdown`, retry; or
2. Run rbx-sync on Windows (T1) against the same files via `\\wsl$\…` or a Windows clone.

## Paths

`rbx-sync.json` disk paths are relative and use `/`. rbx-sync translates to the OS path. `--project` MAY be a Windows path or a POSIX path depending on the process.
